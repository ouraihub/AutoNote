# 44 多仓库 AI 审查与自动合并操作

目标：Aether、AutoOwl、AutoFox、AutoBee、desktop-kit、release-kit 和 AutoNote 一样，PR 经 AI 审查、必需检查全绿后自动合并。

已经完成的部分：6 个仓库都已合入 `.github/workflows/ai-review.yml`（调用 `ouraihub/release-kit/review@v0`）和 `AGENTS.md`；已开启自动合并、合并后删分支、只允许合并提交；变量 `AI_MODEL` 已设为 `gpt-6.1-sol`。

剩下的按顺序做。**第 1 步没做完之前不要做第 3 步**：没有密钥时 AI 审查必然失败，开了分支保护后所有 PR 都会卡住。

| 仓库                   | 必需检查（CI job 名 + `AI review`）                                  |
| ---------------------- | -------------------------------------------------------------------- |
| `ouraihub/Aether`      | `windows`、`macos-core`、`linux-core`                                |
| `ouraihub/AutoOwl`     | `verify`                                                             |
| `ouraihub/AutoFox`     | `Verify (windows)`                                                   |
| `topaihub/AutoBee`     | `Verify (windows)`                                                   |

## 1. 写入密钥

每个仓库需要三个 Secret：

| Name            | 值                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| `AI_BASE_URL`   | `https://autonote.ouraihub.com/relay/v1`                                                                          |
| `AI_API_KEY`    | AutoNote 转发访问密钥。可以沿用 AutoNote 仓库在用的那把，也可以按 `GitHub评审接入AutoNote转发操作.md` §1 另建一把 |
| `RELEASE_TOKEN` | GitHub fine-grained PAT，用于开启自动合并（`GITHUB_TOKEN` 做的合并不会触发 main 上的工作流）                      |

`RELEASE_TOKEN` 按所有者建两把 fine-grained PAT，只授权这几个仓库、只给必要权限。泄露或到期时影响面只限一个所有者：

| 用途                    | Resource owner | Repository access                                  |
| ----------------------- | -------------- | -------------------------------------------------- |
| `T1`（ouraihub 的仓库） | `ouraihub`     | Aether、AutoOwl、AutoFox、desktop-kit、release-kit |
| `T2`（AutoBee）         | `topaihub`     | AutoBee                                            |

- 创建地址：<https://github.com/settings/personal-access-tokens/new>。
- Repository permissions 只开三项 Read and write：**Contents**、**Pull requests**、**Workflows**（PR 改了 `.github/workflows/` 时合并需要这一项）。其余保持 No access。
- 过期时间建议 90 天。到期或怀疑泄露时，在 <https://github.com/settings/personal-access-tokens> 撤销，新建后按本节重新写入对应仓库。
- topaihub 组织若要求审批 fine-grained token，`T2` 创建后要在组织设置里批准才生效。
- AutoNote 自己的 `RELEASE_TOKEN` 不在本文范围内，不要改。

GitHub 的 Secret 写入后读不出来，值要从自己的密码管理器里取。在本机 Git Bash 运行，输入时不回显，不进 shell 历史：

```bash
read -rp "AI_BASE_URL: " U; read -rsp "AI_API_KEY: " K; echo
read -rsp "T1 (ouraihub): " T1; echo; read -rsp "T2 (topaihub): " T2; echo
for r in ouraihub/Aether ouraihub/AutoOwl ouraihub/AutoFox topaihub/AutoBee ouraihub/desktop-kit ouraihub/release-kit; do
  case $r in topaihub/*) T=$T2 ;; *) T=$T1 ;; esac
  printf %s "$U" | gh secret set AI_BASE_URL -R $r
  printf %s "$K" | gh secret set AI_API_KEY -R $r
  printf %s "$T" | gh secret set RELEASE_TOKEN -R $r
done; unset U K T T1 T2
```

检查：每个仓库都应列出这三个名字。

```bash
for r in ouraihub/Aether ouraihub/AutoOwl ouraihub/AutoFox topaihub/AutoBee ouraihub/desktop-kit ouraihub/release-kit; do
  printf '%s: ' $r; gh secret list -R $r --json name -q '[.[].name]|join(",")'
done
```

## 2. 合并 release-kit #7

这个 PR 让 release-please 用 `RELEASE_TOKEN` 开发布 PR。用 `GITHUB_TOKEN` 开的发布 PR 不触发 CI，开了分支保护后必需检查永远不上报，发布 PR 就合不了。

它之前的 `AI review` 失败只是因为当时没有密钥。重跑这次审查：

```bash
gh run rerun $(gh run list -R ouraihub/release-kit -w "AI review" -b ci/release-token -L 1 --json databaseId -q '.[0].databaseId') -R ouraihub/release-kit --failed
```

审查通过后它会自动合并（这时还没有分支保护，会立即合并）。确认：

```bash
gh pr view 7 -R ouraihub/release-kit --json state -q .state   # MERGED
```

审查一直不通过时，看 PR 上的评论处理，不要跳过。

## 3. 开启 main 分支保护

禁止直推和强推，必须走 PR，必需检查按开头的表。

`PUT .../protection` 会整体替换已有配置。下面的函数先确认仓库**没有**分支保护（接口返回 404）才写入；已有保护就停下并打印现有配置，人工合并后再处理，不覆盖。2026-10-25 检查时这 6 个仓库都没有保护。

`enforce_admins=false`：管理员（仓库所有者）仍可绕过，和 AutoNote 一致，用于 AGENTS.md §4 那种经用户同意的管理员合并。

```bash
protect() { repo=$1; shift
  if current=$(gh api repos/$repo/branches/main/protection 2>/dev/null); then
    echo "SKIP $repo: main already protected, not overwriting:"; echo "$current"; return 1
  fi
  checks=$(printf '%s\n' "$@" "AI review" | node -e 'console.log(JSON.stringify(require("fs").readFileSync(0,"utf8").trim().split("\n").map(c=>({context:c}))))')
  printf '{"required_status_checks":{"strict":false,"checks":%s},"enforce_admins":false,"required_pull_request_reviews":{"required_approving_review_count":0},"restrictions":null,"allow_force_pushes":false,"allow_deletions":false}' "$checks" \
    | gh api -X PUT repos/$repo/branches/main/protection --input - -q '"\(.url|split("/")[5]): \([.required_status_checks.checks[].context]|join(", "))"'
}
protect ouraihub/Aether windows macos-core linux-core
protect ouraihub/AutoOwl verify
protect ouraihub/AutoFox "Verify (windows)"
protect topaihub/AutoBee "Verify (windows)"
protect ouraihub/desktop-kit "Check (ubuntu-24.04)" "Check (macos-14)" "Check (windows-latest)"
protect ouraihub/release-kit test
```

每行输出 `仓库名: 检查列表`，列表应与开头的表一致，最后都带 `AI review`。

## 4. 每个仓库用一个 PR 验证

可以用接下来第一个真实改动当验证，也可以开一个只改文档的小 PR。判定标准：

1. PR 页面出现所有必需检查，`AI review` 通过后 PR 上有审查结论评论。
2. 全部检查通过后 PR 自动合并，远端分支被删除。
3. 分支保护生效：`gh api repos/<仓库>/branches/main/protection -q '.required_pull_request_reviews != null'` 输出 `true`。管理员可以绕过，所以不要用自己的账号直推 main 来验证；需要验证直推被拒，用没有管理员权限的协作者账号。

## 5. 常见问题

| 现象                                                              | 处理                                                                                                        |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `AI review` 报 `AI_BASE_URL, AI_API_KEY and AI_MODEL must be set` | 第 1 步漏了这个仓库，补写后重跑失败的 job                                                                   |
| 审查通过但 PR 不合并                                              | 看其他必需检查是否还在跑或失败；`RELEASE_TOKEN` 过期、没授权这个仓库或缺第 1 节的三项权限时，合并步骤会报错 |
| PR 一直显示 `Expected — Waiting for status`                       | 必需检查名和 job 名不一致；改 job 名时要同步改分支保护                                                      |
| 发布 PR（`release-please--*`）没有自动合并                        | 设计如此，发布 PR 不由审查合并。release-kit 的发布 PR 手动 `gh pr merge <n> --merge`                        |
| 模型额度不足、超时                                                | 见 `GitHub评审接入AutoNote转发操作.md` §6；修好后 `gh run rerun <run-id> --failed`，不用改代码              |
