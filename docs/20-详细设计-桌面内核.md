> 其他文档引用本文时：command 清单用 §6，表结构用 §4.2，写入 API 用 §5，远端应用用 §5.6，变更通知用 §5.7，查询用 §11。

## 1. 结论

- `note-core` 是桌面端唯一能读写 `library.db` 和 `data\\files\\` 的代码。GUI command、MCP、同步三个入口都调用同一个 `Library`，走同一条写入流程（§5）。其他 crate 只能调用 `note-core` 的公开领域 API，绝不取得数据库连接。
- D1 迁移只建立桌面内核拥有的核心表：`app_meta`、`schema_migrations`、`folders`、`notes`、`tags`、`note_tags`、`links`、`note_versions`、`attachments`、`changes`、`notes_fts`、`prefs`。**不预建同步表（`sync_binding`、`sync_item`、`sync_attachment`）和 `mcp_tokens`、`mcp_operations`**；D4/D5 的迁移分别在 `22-详细设计-桌面同步与MCP.md` 定义，并由统一迁移链在启用对应功能时追加。
- 行为以 worker 路由为准：`rev`、`content_hash`、`changes`、版本快照、链接、标签的规则逐条对照 `routes/notes.ts`，这样同步两端（D5）看到的是同一套语义。
- 需要和 TS 逐字节一致的纯函数（`segmentCJK`、`deriveExcerpt`、`countText`、`extractTags`、`extractWikiLinks`、`normalizeLinkKey`、26 位 ID）移植到 `note-core::markdown` / `note-core::id`，一致性由共享对照夹具保证（§12）。
- command 层很薄：反序列化参数 → `spawn_blocking` 调用 `Library` → `note_core::Error` 转成 `AppError` → 返回。command 名称与端口方法一一对应，完整清单见 §6。
- 两端的类型一致性由 `desktop/fixtures/ipc-contract.json` 保证（§12）。

### 4.2 迁移 v2

写进 `MIGRATIONS`，整段 SQL 用一次 `execute_batch` 执行（`migrate()` 已经放在同一个事务里）。列名和默认值与 D1 保持一致，这样行映射（`db/rows.rs`）可以逐列对照 worker 的 `db/rows.ts`。本段 SQL 的末尾只能到 `prefs`；D4/D5 表不得出现在 D1 v2。

```sql
CREATE TABLE folders (
  id TEXT PRIMARY KEY, parent_id TEXT, name TEXT NOT NULL,
  icon TEXT, color TEXT, position REAL NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL, deleted_at INTEGER
);
CREATE INDEX idx_folders_parent ON folders(parent_id, position);
CREATE UNIQUE INDEX idx_folders_unique_sibling
  ON folders(IFNULL(parent_id, ''), lower(name)) WHERE deleted_at IS NULL;

CREATE TABLE notes (
  id TEXT PRIMARY KEY, folder_id TEXT,
  title TEXT NOT NULL DEFAULT '', title_key TEXT NOT NULL DEFAULT '',
  content TEXT NOT NULL DEFAULT '', excerpt TEXT NOT NULL DEFAULT '',
  rev INTEGER NOT NULL DEFAULT 1,
  word_count INTEGER NOT NULL DEFAULT 0, char_count INTEGER NOT NULL DEFAULT 0,
  is_pinned INTEGER NOT NULL DEFAULT 0, is_starred INTEGER NOT NULL DEFAULT 0,

);
CREATE INDEX idx_notes_updated ON notes(deleted_at, is_archived, updated_at DESC);
CREATE INDEX idx_notes_folder ON notes(folder_id, updated_at DESC);
CREATE INDEX idx_notes_starred ON notes(is_starred, updated_at DESC);
CREATE INDEX idx_notes_trash ON notes(deleted_at);
CREATE INDEX idx_notes_title_key ON notes(title_key, deleted_at, created_at, id);

);
CREATE UNIQUE INDEX idx_tags_unique ON tags(name);
CREATE INDEX idx_tags_name_nocase ON tags(name COLLATE NOCASE);

CREATE TABLE note_tags (note_id TEXT NOT NULL, tag_id TEXT NOT NULL, PRIMARY KEY (note_id, tag_id));
CREATE INDEX idx_note_tags_tag ON note_tags(tag_id);

CREATE TABLE links (
  source_note_id TEXT NOT NULL, target_key TEXT NOT NULL,
  target_title TEXT NOT NULL, target_note_id TEXT,
  PRIMARY KEY (source_note_id, target_key)
);
CREATE INDEX idx_links_target ON links(target_key);
CREATE INDEX idx_links_target_note ON links(target_note_id);

CREATE TABLE note_versions (
  id TEXT PRIMARY KEY, note_id TEXT NOT NULL, title TEXT NOT NULL,
  content TEXT NOT NULL, size INTEGER NOT NULL, created_at INTEGER NOT NULL
);
CREATE INDEX idx_versions_note ON note_versions(note_id, created_at DESC, id DESC);

CREATE TABLE attachments (
  id TEXT PRIMARY KEY, note_id TEXT, filename TEXT NOT NULL, mime TEXT NOT NULL,
  size INTEGER NOT NULL, sha256 TEXT NOT NULL, width INTEGER, height INTEGER,
  storage TEXT NOT NULL DEFAULT 'local' CHECK (storage IN ('local')),
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_attachments_created ON attachments(created_at DESC);
CREATE INDEX idx_attachments_sha ON attachments(sha256);
CREATE INDEX idx_attachments_note ON attachments(note_id);

CREATE TABLE changes (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  entity TEXT NOT NULL CHECK (entity IN ('note','folder','tag','settings')),
  entity_id TEXT NOT NULL, op TEXT NOT NULL CHECK (op IN ('upsert','delete')),
  at INTEGER NOT NULL
);

CREATE VIRTUAL TABLE notes_fts USING fts5(

CREATE TABLE prefs (key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at INTEGER NOT NULL);

```

说明：

- `notes_fts.note_id` 标成 `UNINDEXED`，和 D1 不同。原因：D1 用 `note_id : "<id>"` 做 MATCH 删除（`db/fts.ts` 的 `FTS_NOTE_MATCH_SQL`），而桌面只用 `DELETE FROM notes_fts WHERE note_id = ?1`，不需要对 ID 分词。这样 ID 片段也不会误命中关键词搜索。
- 不开外键约束。`Library::open` 虽然设置了 `foreign_keys`，但 D1 schema 本身没有声明 `REFERENCES`，桌面也不加，保持与 D1 一致：级联删除在写入流程里显式执行。
- `changes` 只保留最近 `LIMITS.changeLogKept`（5000）条。worker 的做法是在定时任务 `backup/scheduler.ts` 的 `trimChangeLog`（第 130–155 行）里删除最近 5000 条之前的记录。桌面在 `Library::open` 成功后执行一次同样的 SQL（去掉 `user_id` 条件），不在每次写入时执行。

## 5. 统一写入流程

### 5.1 `Library`：连接、锁与事务

`core/src/db/mod.rs`：

```rust
pub struct Library {
    conn: std::sync::Mutex<rusqlite::Connection>,
    files_dir: PathBuf,                 // <data>\files
    clock: Arc<dyn Clock>,
    ids: Arc<dyn IdSource>,
    sink: Arc<dyn ChangeSink>,
}

pub struct LibraryDeps { pub clock: Arc<dyn Clock>, pub ids: Arc<dyn IdSource>, pub sink: Arc<dyn ChangeSink> }

impl Library {
    /// # Errors  `Error::Sqlite` / `Error::SchemaTooNew` / `Error::Io`
    pub fn open(data_dir: &Path, deps: LibraryDeps) -> Result<Self, Error>;
    /// 测试用：内存库 + 临时 files 目录
    pub fn open_in_memory(files_dir: &Path, deps: LibraryDeps) -> Result<Self, Error>;
    pub fn schema_version(&self) -> Result<i64, Error>;

    pub(crate) fn read<T>(&self, f: impl FnOnce(&Connection) -> Result<T, Error>) -> Result<T, Error>;
    pub(crate) fn write<T>(
        &self,
        origin: WriteOrigin,
        f: impl FnOnce(&mut WriteTx<'_>) -> Result<T, Error>,
    ) -> Result<Written<T>, Error>;
}
```

- `Library` 是 `Send + Sync`，根包用 `Arc<Library>` 注册，command 拿到的是 `State<'_, Arc<Library>>`，碰不到 `Mutex`（工程规范 §7）。
- 锁中毒映射为 `Error::Poisoned`，不 panic（工程规范 §4.3）。
- `open` 的签名从 `&Path`（库文件）改成 `data_dir`，由它自己拼出 `library.db` 和 `files\`，并在第一次打开时创建 `files\`。`shell::paths::library_db` 保留给 `app_info` 显示路径用。
- `write`：加锁 → `conn.transaction_with_behavior(Immediate)` → 构造 `WriteTx { tx, origin, now, changes: ChangeSet::default() }` → 执行 `f` → 刷 FTS（见 §5.4 第 7 步）→ `commit` → 释放锁 → `sink.library_changed(&changes)`（只有 `changes` 非空时才调用）。`f` 返回 `Err` 时整个事务回滚，也不通知。
- `WriteTx` 是 crate 内部类型，提供 `record_change(entity, id, op)`、`touch_note(summary)`、`delete_note(id)`，并在 `changes` 中收集本事务触及的笔记、文件夹、标签 id。D5 启用后，`Library::write` 在提交前对 `origin != Sync` 的写入按这些 id 登记 `sync_item.dirty=1`（22 §6.2），与业务写入同一事务。只有 `write/`、`files.rs` 以及 22 的 `sync.rs`、`mcp.rs` 会使用这些内部能力。
- `pub(crate)` 意味着 note-sync、note-mcp 不能直接拿到连接。它们需要的每一种读写都在 note-core 里以 `pub fn` 暴露。这样「SQL 只在 note-core」（`core/src/lib.rs` 第 3–4 行的约束）是由编译器保证的。

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum WriteOrigin { Ui, Mcp, Sync, Import }

pub struct Written<T> { pub value: T, pub changes: ChangeSet }

#[derive(Debug, Default, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct ChangeSet {
    pub notes: Vec<NoteSummary>,   // 本事务中最终状态的摘要，按 id 去重，保留最后一次
    pub deletions: Vec<String>,    // 彻底删除（purge）的笔记 id；软删除走 notes（带 deletedAt）
    #[serde(skip)] pub folders_changed: bool,
    #[serde(skip)] pub tags_changed: bool,
    #[serde(skip)] pub settings_changed: bool,
    #[serde(skip)] pub origin: Option<WriteOrigin>,
}
```

### 5.2 ID、时钟、哈希

**ID**（`core/src/id.rs`），逐行对照 `web/src/worker/lib/id.ts`：

```rust
pub const ALPHABET: &[u8; 32] = b"0123456789abcdefghjkmnpqrstvwxyz";

/// 前 10 位：毫秒时间戳的 base32，高位在前（id.ts 第 7–12 行）；
/// 后 16 位：每个随机字节 & 31 后查表（第 13–16 行）。
pub fn encode_id(millis: u64, random: &[u8; 16]) -> String;
pub fn is_valid_id(s: &str) -> bool;       // ^[0-9a-hjkmnp-tv-z]{26}$（第 45–48 行）
pub fn id_time(s: &str) -> u64;            // 前 10 位解码，遇到非法字符返回 0（第 35–43 行）

pub trait IdSource: Send + Sync { fn new_id(&self, now: Millis) -> String; }
pub struct RandomIds;                      // 用 getrandom 取 16 字节后调用 encode_id
```

- `encode_id` 是纯函数：时间戳用 `n % 32` 取余，循环 10 次，不足的高位自然补 `0`，与 TS 一致。
- 测试用 `SequentialIds`（放在 `#[cfg(test)]` 里）：固定的前缀加上自增计数，保证快照结果稳定。
- ID 与 TS 是否一致，由对照夹具中的 `id` 分组保证（§12）：给定 `millis` 和 `random`，两边输出的字符串必须相同。

**时钟**（`core/src/clock.rs`）：`pub trait Clock: Send + Sync { fn now(&self) -> Millis; }`，生产用 `SystemClock`，测试用 `FixedClock(AtomicI64)`，可以手动推进。写入一律使用 `WriteTx.now`（事务开始时取一次），不在函数内部另外调用 `SystemTime`。

**哈希**：`content_hash = hex(sha256(content.as_bytes()))`，输出小写十六进制。对照 `lib/encoding.ts` 的 `sha256Hex`（第 56–60 行，UTF-8 编码）和 `toHex`（第 41–46 行，小写，两位补零）。使用 `sha2` crate。

**`updated_at` 单调递增**：修改时 `now = max(clock.now(), row.updated_at + 1)`，对照 `routes/notes.ts` 第 391 行。

### 5.3 笔记写入 API

`core/src/write/notes.rs`。全部都是 `impl Library` 上的 `pub fn`，返回 `Result<Written<T>, Error>`：

```rust
pub struct NewNote { pub id: Option<NoteId>, pub title: Option<String>, pub content: String,
                     pub folder_id: Option<FolderId>, pub is_starred: bool }
pub struct NotePatch { pub rev: Rev, pub title: Option<String>, pub content: Option<String>,
                       pub folder_id: Option<Option<FolderId>>,   // None = 不改；Some(None) = 移出文件夹
                       pub is_pinned: Option<bool>, pub is_starred: Option<bool>, pub is_archived: Option<bool>,
                       pub quiet: bool, pub preserve_version: bool }

impl Library {
    pub fn create_note(&self, input: &NewNote, origin: WriteOrigin) -> Result<Written<Note>, Error>;
    pub fn patch_note(&self, id: &NoteId, patch: &NotePatch, origin: WriteOrigin) -> Result<Written<Note>, Error>;
    pub fn trash_note(&self, id: &NoteId, origin: WriteOrigin) -> Result<Written<NoteSummary>, Error>;
    pub fn restore_note(&self, id: &NoteId, origin: WriteOrigin) -> Result<Written<NoteSummary>, Error>;
    pub fn purge_note(&self, id: &NoteId, origin: WriteOrigin) -> Result<Written<()>, Error>;
    pub fn empty_trash(&self, origin: WriteOrigin) -> Result<Written<u64>, Error>;
    pub fn duplicate_note(&self, id: &NoteId, origin: WriteOrigin) -> Result<Written<Note>, Error>;
    pub fn restore_version(&self, id: &NoteId, version: &VersionId, rev: Rev, origin: WriteOrigin)

```

`NewNote` 和 `NotePatch` 与 `@shared/types` 的 `CreateNoteBody`、`PatchNoteBody` 同形状，由 `dto.rs` 用 serde 反序列化后转换过来。`folder_id` 用双层 `Option` 区分「没有传」和「传了 null」：`#[serde(default, deserialize_with = "double_option")]`。

### 5.4 笔记写入步骤

逐条对照 `web/src/worker/routes/notes.ts`：创建在第 257–341 行，修改在第 343–567 行，派生数据在 `db/writes.ts` 的 `buildNoteDerivedStatements`（第 82–239 行）。D1 需要 CAS 守卫来处理并发；桌面虽只有一个写事务串行化入口，**仍必须验证调用者提供的本地 `rev`**，单写者只消除数据库写入竞争，不代表可以取消过期编辑检查。远端 `remote_rev` 是独立域，不能与本地 `rev` 比较或替代它；只有 §5.6 的远端应用 API 接受单独的 `remote_rev`。

**创建 `create_note`**

1. 校验：传了 `id` 就必须满足 `is_valid_id`，否则返回 `Error::InvalidInput`；`content` 的 UTF-8 字节数超过 `LIMITS.contentMaxBytes`（2 MiB）时返回 `Error::TooLarge`（对照 `lib/request.ts` 的 `assertContentSize`）。
2. 幂等：`id` 已经存在（包括在回收站里的）时，直接返回现有的 `Note`，`changes` 为空。对照第 281–292 行。桌面没有多个用户，所以不存在「被别人占用」的冲突分支。
3. `title = resolve_title(input.title, "")`：`trim` 之后按 UTF-16 截到 512（对照第 1166–1168 行）。**标题不从正文推导**，与 worker 一致。
4. `folder_id` 必须指向一个未删除的文件夹，否则返回 `Error::NotFound(Entity::Folder)`。
5. `INSERT` 一行：`rev = 1`，`position = now`（第 303 行 `?10 = now`），`excerpt = derive_excerpt`，`word_count` 和 `char_count` 来自 `count_text`，再加上 `content_hash`，`created_at = updated_at = now`。
6. 执行派生步骤 `derive(tx, id, title, content, prev_title = None)`，见下文。
7. `record_change(Note, id, Upsert)`，`touch_note(summary)`；若 D5 同步 schema 已启用，再由同一事务的可选 outbox hook 记录 create 操作。

**修改 `patch_note`**

1. 读出当前行。不存在时返回 `Error::NoteGone { deletion_cursor }`，其中 `deletion_cursor = SELECT MAX(seq) FROM changes WHERE entity='note' AND entity_id=? AND op='delete'`（对照第 354–362 行）。
2. `patch.rev < 1` 时返回 `InvalidInput`；`patch.rev != row.rev` 时返回 `Error::Conflict { server: Box<Note> }`（对照第 364–369 行）。
3. `now = max(clock, row.updated_at + 1)`。
4. 正文：`content` 有值、和旧值不同、哈希也不同时，才算 `content_changed`。这时同时写入 `content`、`content_hash`、`title`（取解析后的新标题）、`excerpt`、`word_count`、`char_count`。只改了标题时只写 `title`（对照第 400–419 行）。
5. `folder_id`、`is_pinned`、`is_starred`、`is_archived`：只在值不同时写入（对照第 421–426 行）。
6. 没有任何字段变化时，直接返回当前行，`rev` 不变，也不写 `changes`（对照第 428 行）。
7. 有变化时 `rev += 1`，`updated_at = now`。
8. 版本快照（`write/versions.rs`），条件是 `content_changed && !quiet && !row.content.is_empty()`，并且下面任一项成立（对照第 447–471 行）：`preserve_version`；这篇笔记还没有任何版本；`now - MAX(created_at) > SNAPSHOT_INTERVAL_MS`（5 分钟）；新旧正文的 **UTF-16 长度**之差的绝对值 ≥ `SNAPSHOT_DIFF_THRESHOLD`（400）。快照内容是修改**之前**的 `title` 和 `content`，`size` 取旧正文的 UTF-8 字节数。插入后删除最新 `LIMITS.versionsPerNote`（50）条以外的旧版本。
9. 笔记未被删除，并且正文或标题有变化时，执行 `derive(...)`。标签集合发生变化时，再删除 `is_manual = 0` 且没有任何笔记引用的标签（对照第 474–500 行）。
10. 标题改了、并且没有其他未删除的笔记的 `title_key` 等于新旧两个 key 中的任何一个时，调用 `rewrite_inbound_links(tx, id, old_title, new_title)`，在**同一个事务**里改写其他笔记正文中的 `[[旧标题]]`（对照第 519–558 行和第 1003–1099 行的 `rewriteInboundWikiLinks`）。每一篇被改写的笔记都走一遍完整的「修改」流程：`rev + 1`、**无条件**保存一个快照、执行派生步骤、写 `changes`、写 outbox，并把它的摘要放进 `ChangeSet.notes`。有歧义时只重新解析 `links.target_note_id`。D1 在这里有最多 5 次的重试，是为了应对并发 CAS 失败；桌面在同一个事务里执行，不需要重试。
11. `record_change(Note, id, Upsert)`，`touch_note`；若 D5 同步 schema 已启用，再由同一事务的可选 outbox hook 记录 patch 操作（带 `old_rev`）。

**派生步骤 `derive`**（`write/derived.rs`，对照 `buildNoteDerivedStatements`）：

1. `UPDATE notes SET title_key = normalize_link_key(title)`。
2. 标签：`names = extract_tags(content)`。对每个 name 按 `COLLATE NOCASE` 查找已有标签，有多个候选时，优先选名称完全相同的，其次选 `created_at, id` 最小的（对照第 119–129 行的 `ranked_tags`）。找不到就新建（`is_manual = 0`）。然后把 `note_tags` 替换成这组 tag id。
3. 链接：`links = extract_wiki_links(content)`（笔记已删除时为空），删除不在这组 key 里的链接；`UPSERT (source, key, target_title, target_note_id)`，其中 `target_note_id` 取 `title_key = key AND deleted_at IS NULL ORDER BY created_at, id LIMIT 1` 的那篇笔记（对照第 174–206 行）。
4. 标题改了时，把所有 `target_key IN (新 key, 旧 key)` 的链接重新解析 `target_note_id`（对照第 221–236 行和 `LINK_TARGET_SUBQUERY`）。
5. FTS：笔记未删除时执行 `DELETE FROM notes_fts WHERE note_id=?`，然后 `INSERT (note_id, segment_cjk(title), segment_cjk(truncate_utf16(content, LIMITS.ftsContentChars)))`；已删除时只执行 DELETE。直接写入，不经过队列（对照 `db/fts.ts` 第 58–72 行的分词和截断方式）。

不变量（D1-4 的测试逐条覆盖）：

- I1：`notes_fts` 里有某篇笔记的行，当且仅当这篇笔记的 `deleted_at IS NULL`。
- I2：`content_hash == sha256_hex(content)`；`word_count`、`char_count`、`excerpt` 等于对当前正文重新计算的结果。
- I3：每次成功的、有实际变化的写入，`rev` 严格加 1，并且恰好多出一条 `changes`；没有变化的写入这两者都不变。
- I4：`note_tags` 等于 `extract_tags(content)` 映射出来的标签集合；没有被引用、并且 `is_manual = 0` 的标签不存在。
- I5：`links` 等于 `extract_wiki_links(content)` 的 key 集合；`target_note_id` 指向 `title_key` 匹配的笔记里最早创建的那一篇。
- I6：每篇笔记最多保留 50 个版本。

### 5.5 组织操作

文件夹和标签没有本地 `rev`，但每个变更仍必须通过同一个 `Library::write` 事务和 `ChangeSet`。输入名称先做 Unicode trim、空值/长度校验；同一父文件夹下的活动文件夹名称不区分大小写唯一，标签名称全库不区分大小写唯一。位置排序只接受有限数字，NaN、无穷和溢出返回 `bad_request`。

文件夹删除明确接受 `strategy: 'move-up' | 'delete'`：`move-up` 将子文件夹提升到被删文件夹的父级，并把该文件夹内笔记移动到同一父级；`delete` 删除整个子树，并将其中笔记软删除（递增各自本地 rev、重算派生数据和 FTS），关系清理在同一事务完成。不能把两种策略都简化为移到根目录。

标签删除不能只删 `note_tags` 关联：这会使下次正文派生从 `#tag` 重新创建标签。删除标签时必须在同一事务中，按 worker `tags.ts` 的替换规则改写仍引用该标签的未删除笔记正文，递增每篇本地 rev、更新 hash/excerpt/count/versions/links/FTS，并将 affected 计入结果；之后删除标签及关联。若没有可安全改写的引用，按冲突返回，不静默只删关联。

```rust
pub struct FolderInput { pub parent_id: Option<FolderId>, pub name: String, pub icon: Option<String>, pub color: Option<String>, pub position: f64 }
pub struct TagInput { pub name: String, pub color: Option<String> }
pub enum FolderDeleteStrategy { MoveUp, Delete }
impl Library {
    pub fn list_folders(&self, include_deleted: bool) -> Result<Vec<Folder>, Error>;
    pub fn create_folder(&self, input: &FolderInput, origin: WriteOrigin) -> Result<Written<Folder>, Error>;
    pub fn patch_folder(&self, id: &FolderId, input: &FolderInput, origin: WriteOrigin) -> Result<Written<Folder>, Error>;
    pub fn remove_folder(&self, id: &FolderId, strategy: FolderDeleteStrategy, origin: WriteOrigin) -> Result<Written<FolderDeleteResult>, Error>;
    pub fn list_tags(&self) -> Result<Vec<Tag>, Error>;
    pub fn create_tag(&self, input: &TagInput, origin: WriteOrigin) -> Result<Written<Tag>, Error>;
    pub fn patch_tag(&self, id: &TagId, input: &TagInput, origin: WriteOrigin) -> Result<Written<TagPatchResult>, Error>;
    pub fn remove_tag(&self, id: &TagId, origin: WriteOrigin) -> Result<Written<TagRemoveResult>, Error>;
}
```

提交前只写数据库和本地附件暂存区，提交后才发事件、日志完成事件和出站状态；事务失败不得产生半成品通知。跨请求幂等由 D4 的 operationId 事务合同负责，D1 API 不将 mutationId 误作本地 rev。

### 5.6 远端应用边界

同步 crate 不取得 `Connection`、`Mutex` 或 `WriteTx`。`note-core` 只暴露 22 §8.1 列出的同步领域 API。远端 `remote_rev` 只存于 `sync_item`，永远不写入或比较 `notes.rev`；`cursor` 只推进同步状态，不充当笔记修订号。

远端应用在一个本地事务内完成内容、派生表、`changes` 与本地通知，写入来源为 `WriteOrigin::Sync`，因此不登记脏标记。服务器不提供 remote operation id，幂等由客户端指定 id 的创建和 `rev` CAS 保证。旧 cursor 不得倒退。远端数据不得覆盖 `dirty=1` 的本地记录；笔记冲突按 22 §7.3 生成冲突副本，保留双方版本。

### 5.7 提交后事件

`ChangeSink::library_changed(ChangeSet)` 只在事务 commit 成功、连接锁释放后调用。适配器将其转换为 `autonote://library-changed`，载荷为本地 `SyncResponse`（本地 cursor、notes、folders、tags、deletions），不包含正文，也不把 `remote_rev` 冒充本地 `rev`。同一事务只发一个 library 事件；事件发送失败只记录脱敏错误，不回滚已提交数据。

写队列结果是同一 `changes` 总线中的 `kind: 'write'`，不是第二个 watchWrites 总线。`WriteQueueEvent` 严格复用 10 §2 的 `pending|settled|recovered|failed`：pending 只含 count；settled/recovered/failed 均带 writeId 和 noteId，failed 带 code/retained。桌面本地事务不会生成 queued 结果，正文失败保留编辑缓冲，事件处理不得覆盖之后输入。设置变更发 settings，连接状态发 connectivity。

## 7. 领域类型与错误

newtype `NoteId`、`FolderId`、`TagId`、`AttachmentId`、`VersionId`、`Rev`、`Millis` 在构造时校验；ID 必须是 26 位 Crockford base32，`Rev >= 1`，毫秒时间为非负 i64。DTO 使用 `#[serde(rename_all = "camelCase")]`，对外不暴露 SQL 行或连接。

内部 `Error` 变体至少包括 `InvalidInput`、`NotFound { entity, id }`、`NoteGone { deletion_cursor }`、`Conflict { server }`、`TooLarge { limit }`、`Sqlite`、`Io`、`SchemaTooNew`、`Poisoned`、`Offline` 和 `Cancelled`。IPC 映射严格使用概要设计错误码：输入→`bad_request`，长度→`payload_too_large`，不存在→`not_found`，本地 rev 冲突→`conflict`（details.server），锁/数据库/迁移→`internal` 或 `storage_unavailable`；取消→客户端专用 `cancelled`，超时→`request_timeout`，响应解析失败→`invalid_response`。这些客户端错误不改 worker HTTP 集合，也不得把内部错误名泄露给客户端；`details` 只放安全结构化字段，绝不放路径、SQL、正文或底层异常。

## 8. Markdown 纯函数的 Rust 移植

`core/src/markdown` 只放无 I/O、无时钟、无全局状态的函数：`segment_cjk`、`truncate_utf16`、`derive_excerpt`、`count_text`、`extract_tags`、`extract_wiki_links`、`normalize_link_key`、`sha256_hex`。输入字符串按 Rust UTF-8 读取；**UTF-8 字节界限只用于 payload/content 大小和哈希，UTF-16 code unit 界限只用于标题 512、excerpt/搜索截断和版本 diff 阈值**，禁止用字节索引切断字符。每个截断函数必须在 code point 边界返回合法 UTF-8，并按 TS 的 surrogate/code-unit 语义计数。

ID 编码也是纯函数，固定 alphabet、时间高位序列和随机字节映射；`id_time` 遇非法输入返回 0，构造 newtype 则返回 `bad_request`。对照夹具逐项覆盖中英文、emoji（非 BMP）、组合字符、CRLF、空值、超界和重复标签/链接。

## 9. 附件存储与 `autonote-file` 协议

附件不能假设文件系统与 SQLite 同一事务。IPC 不接收浏览器 `File` 对象：桌面宿主通过 `files_upload_begin/chunk/finish/cancel` 上传；begin 返回随机短期 `uploadId` 和 `chunkMaxBytes`，uploadId 绑定窗口，chunk 必须是原始 binary（Tauri Request 或已验证等价传输），带严格递增 `offset`，禁止把字节编码成 `Vec` JSON 数组。上传会话空闲 5 分钟或窗口断开即回收，finish 成功后 uploadId 不可复用。路径必须由 21 的 dialog/宿主接缝提供，core 只接收经过校验的输入流/块。先写 `<data>/files/.stage/<attachmentId>.<random>.part`，流式计算大小和 SHA-256，限制 `LIMITS.attachmentMaxBytes`，完成后 `fsync`，再同目录原子 rename 到 `<data>/files/<id>`；最后在 SQLite 事务写 attachment 元数据。若数据库提交失败，stage/final 文件进入可恢复清单，不可直接删除可能被引用的文件；定期 prune 只删除未被 `attachments` 引用且超过保留窗口的对象，并排除用户 data 下任何非附件路径。

崩溃恢复启动时扫描 stage 和 final：有元数据无文件→`storage_unavailable`/损坏事件；有文件无元数据→仅当 age 超过窗口才清理，否则保留供恢复；stage 不参与协议读取。协议校验 ID 字符集、规范化路径、最终路径必须仍在 files 根目录内，禁止 `..`、符号链接逃逸和任意 URL。响应正确 MIME/长度并使用流式读取；`autonote-file://` 只映射附件，不开放目录。

## 10. 事件与进度

D1领域事件为 `autonote://library-changed`（ChangeFeed适配library）；设置变更由载荷flags转settings。D4/D5服务状态事件另见22，不与领域事件混为一谈。事件在commit、解锁后发出，失败不回滚已提交数据；窗口经library_changes补拉。

导入、导出、附件上传、重建索引等单调用高频进度使用 `tauri::ipc::Channel<ProgressEvent>`，字段严格为 `{jobId, phase, completed, total, terminal}`，phase 仅为 `validating|reading|writing|uploading|finalizing`，`total` 可为 null。成功、失败、取消都通过 command 的 `Result` 和最后一个 `terminal=true` 进度项表达，进度项不新增 `error` 字段；发送 terminal 后不得再发事件。取消 command 按 jobId 设置取消标记，业务在安全边界检查并回滚未提交事务，不以丢弃 Promise 代替取消。

## 11. 查询

查询只读 `Library::read`，不把连接泄露给调用方。`list_notes` 支持 cursor、limit（1–200）、folder、tag、archived、starred、trash 和排序白名单；未知字段、负数、过大 limit 返回 `bad_request`。`get_note` 默认返回正文，列表只返回摘要；不存在的已删除笔记返回 `not_found` 与 deletionCursor。`search_query` 优先 FTS5，FTS 不可用时仅在明确记录 warn 后回退受参数限制的 LIKE；查询参数均绑定，不能拼接 SQL。

`search_graph` 返回 `GraphResponse`，节点/边及 `meta.truncated` 截断标记，不使用分页游标；`backlinks` 按 target key 和 target_note_id 查询并去重。`list_versions` 按 createdAt/id 稳定降序，`get_version` 限定 noteId。`settings_get` 按分区读取 prefs，非法 JSON 或未知 schema 返回 `internal`，不静默丢弃设置。

## 12. 契约夹具与测试

`desktop/fixtures/ipc-contract.json` 覆盖合法与边界 DTO、毫秒时间、null/缺省、错误 code/details、冲突 server、queued writeId、SyncResponse 的 cursor/folders/tags/deletions、library_changes 过期 since 的 full snapshot、附件 upload session/offset/finish 生命周期。Rust 测试通过真实 `Library` 产生结果，TS 测试解析同一 JSON 形状；比较 JSON 结构和值，不比较键顺序、空白或序列化字节。

行为契约必须覆盖：D1 初次迁移不出现 sync/mcp 表；rev 过期即使单写者也返回 conflict；UTF-8 payload 与 UTF-16 截断边界；同一事务多笔记/组织变更只发一个提交后事件；D4 事务级相同 operationId 重放返回同结果；D5 独立 remote_rev/cursor 不污染本地 rev；library_changes 在 cursor 过期时返回 full snapshot；附件 DB/FS 崩溃恢复、路径穿越拒绝、超过限制拒绝、断窗/空闲回收及 finish 不可复用；列表/搜索/图谱的过滤、`meta.truncated` 和非法参数错误。测试不得把源码字符串或转发回显当作行为证明。

## 13. 日志事件

使用注入的结构化 Logger/tracing，事件名固定为 `library.open.completed`、`library.migration.failed`、`notes.save.completed`、`notes.save.conflict`、`notes.save.failed`、`organization.change.completed`、`sync.remote.apply.completed`、`attachment.stage.failed`、`attachment.recovery.completed`、`query.search.fallback`、`ipc.command.failed`。字段只含资源 ID、operation ID、write ID、计数、状态码、耗时和安全原因；禁止正文、标题、附件内容、token、cookie、DPAPI 密文、SQL 和完整路径。每个错误只在最终处理层记录一次，循环操作只记录汇总。

## 14. 实施计划

### D1-1 类型与错误

- **依赖**：S0-1、S0-2
- **改动范围**：`desktop/src-tauri/core/src/{types,error,dto,lib}.rs`、`desktop/src-tauri/src/commands/mod.rs`
- **不做**：数据库表、业务写入、D4/D5 API
- **步骤**：1. 建立 newtype、DTO 和安全 `AppError`。2. 实现内部错误到概要设计 code 的映射。3. 导出唯一 core 入口并确认无连接类型公开。
- **判据**：非法 ID/rev/时间得到 `bad_request`；冲突包含安全 server DTO；未知内部错误不泄露 SQL/路径；Rust 编译检查通过。
- **陷阱**：不能把 `AppError` 当 core 内部错误；不能用字符串 message 分支；`remote_rev` 不得复用 `Rev`。

### D1-2 Schema 与迁移

- **依赖**：D1-1
- **改动范围**：`core/src/db/{mod,migrations,rows}.rs`
- **不做**：`sync_*`、`mcp_*` 表及其服务
- **步骤**：1. 追加 D1 v2 核心表和 FTS。2. 在一个事务应用迁移并拒绝 schema too new。3. 保证重复启动幂等并保留已发布迁移。
- **判据**：新库有核心表、无 sync/mcp 表；重启不重复迁移；旧库升级原子完成；迁移失败不留下半套表。
- **陷阱**：不能把 22 的表提前塞进 v2；禁止修改旧迁移；SQL 参数化。

### D1-3 纯函数

- **依赖**：D1-1
- **改动范围**：`core/src/{id,markdown}/`、对照夹具
- **不做**：数据库 IO、网络、解析器状态
- **步骤**：1. 逐个移植并固定 UTF-8/UTF-16 边界。2. 对照 TS 夹具。3. 覆盖非 BMP、组合字符和超界输入。
- **判据**：固定输入与 TS 结果相同；截断不产生非法 UTF-8 或半 surrogate；哈希字节一致；超界输入返回明确错误。
- **陷阱**：Rust `chars().count()` 不等于 UTF-16 长度；不得按字节切字符串。

### D1-4 笔记写入

- **依赖**：D1-2、D1-3
- **改动范围**：`core/src/write/{mod,notes,derived,versions}.rs`
- **不做**：远端同步、MCP tool、UI 乐观状态
- **步骤**：1. 通过单一 IMMEDIATE 事务实现创建/patch/删除/恢复/版本。2. 仍校验本地 rev。3. 同步派生 FTS、标签、链接、版本和 changes。4. 由 ChangeFeed 发出 10 §2 规定的 pending/settled/recovered/failed 写事件，不引入 mutationId 状态字段。
- **判据**：过期 rev 返回 conflict；无变化不增 rev/changes；变化严格增 rev；失败全回滚；FTS/标签/链接/版本不变量成立。
- **陷阱**：单写者不是取消 rev 检查的理由；GUI/MCP 不自动 rebase；只网络回放可按 22 策略恢复。

### D1-5 文件夹与标签

- **依赖**：D1-2、D1-4
- **改动范围**：`core/src/write/{folders,tags}.rs`、组织 DTO
- **不做**：远端 CAS、账号权限
- **步骤**：1. 实现名称、父级、排序验证。2. 在事务内维护软删、关系与 changes。3. 输出集合变更 ChangeSet。
- **判据**：重复名称拒绝；删除文件夹不遗留孤儿引用；标签关联正确；非法排序/名称返回 bad_request；一个事务只发一次事件。
- **陷阱**：组织实体无 rev，不能伪造 rev；软删与彻底删语义不可混用。

### D1-6 查询

- **依赖**：D1-2、D1-3、D1-4
- **改动范围**：`core/src/query/`、`core/src/prefs.rs`
- **不做**：网络搜索、MCP 专用授权
- **步骤**：1. 实现列表、正文、版本、反链、搜索、图谱、设置查询。2. 绑定参数并限制列表输入。3. 增加 FTS 不可用时的受控回退日志；图谱返回 `meta.truncated`，不分页。
- **判据**：列表边界正确；未知参数拒绝；删除游标和冲突 DTO 正确；FTS/LIKE 结果遵循同一过滤规则；图谱截断标记准确。
- **陷阱**：禁止拼接 SQL；不得把连接返回上层；全文查询不能无限 LIKE。

### D1-7 附件

- **依赖**：D1-1、D1-2、D1-4
- **改动范围**：`core/src/files.rs`、根包 `protocol.rs`、附件 command/capability
- **不做**：任意目录浏览、远端对象存储、浏览器 File 直传
- **步骤**：1. 实现 begin/chunk/finish/cancel，使用原始 binary chunk。2. 实现 stage、哈希/大小限制、fsync、rename 和 DB 元数据。3. 实现启动恢复与引用保护。4. 注册严格的 `autonote-file` 协议。
- **判据**：超限、路径穿越、非法 ID 拒绝；DB 失败后文件可恢复且不误删；协议只能读取 files 根内已登记附件；prune 不触碰用户 data 其他目录。
- **陷阱**：FS 与 DB 非同一事务；不能先删除旧文件再提交新引用；协议不是 capability 名。

### D1-8 IPC 事件

- **依赖**：D1-4、D1-5、D1-6、D1-7
- **改动范围**：`desktop/src-tauri/src/{lib,events,commands}/`、`desktop/fixtures/ipc-contract.json`
- **不做**：D2 transport 实现、D4/D5 service
- **步骤**：1. 注册完整 D1 command 表及宿主内部 `library_changes({since})`。2. 注入 ChangeSink 并在锁释放后 emit library changed。3. 为耗时 command 接入 Channel 和 jobId 取消。4. 用真实 core 结果填充夹具。
- **判据**：所有 command 为 async + spawn_blocking + Result；`library_changes` 对过期 since 返回完整 snapshot 且 cursor 仅本地；附件 begin/chunk/finish/cancel 严格按 uploadId、offset、窗口和原始 binary 合同执行；事件只在 commit 后发送且载荷符合 SyncResponse；终端进度唯一且字段严格对齐 10 §2；错误 code/details 与夹具一致；其他 crate 无数据库连接访问。
- **陷阱**：不要用全局 progress 事件或第二写事件总线；不要在 command 写业务逻辑；事件失败不能回滚提交。

## 15. 明确裁决

1. **D1 不预建 sync/mcp 表。** 原因是核心首次启动不应创建未启用功能的 schema；D4/D5 在 22 追加迁移并由统一迁移链串接。
2. **单写者仍检查本地 rev。** 串行化只解决数据库竞争，不能让过期 GUI/MCP 缓冲覆盖新内容。
3. **三域分离。** 本地 `notes.rev`、远端 `remote_rev`、同步 `cursor` 是独立类型和序列；远端应用 API 必须显式传入 remote_rev，绝不复用本地 rev。
4. **边界分离。** UTF-8 字节数用于内容/payload 限制与哈希；UTF-16 code units 用于标题、文本截断和版本差异；不以 `String::len` 代替 UTF-16 规则。
5. **数据库封装。** `Connection`/`WriteTx` 仅在 note-core crate 内可见；MCP、同步、command 只能调用领域 API。
6. **事件与进度。** ChangeFeed 只有一个 changes 总线；写结果并入其中；进度使用 IPC Channel，不能建立 progress 全局事件。
7. **附件安全。** FS 与 DB 按 stage/rename/引用保护/启动恢复协作，不宣称跨系统事务；协议只读已登记 files 根内对象。
8. **D4 幂等边界。** `operationId` 的查询、判重、写入结果必须与业务写入在同一 core 事务；重复请求返回原结果，不重新执行副作用。
9. **D5 远端冲突。** 只有网络回放允许 22 规定的 preserveVersion 恢复策略；GUI/MCP 冲突返回结构化错误，不静默 rebase。
