## 2. 思考合同

- `ReasoningEffort`：`default/none/minimal/low/medium/high/xhigh/max`。default表示不主动设置；none是显式关闭，不等于缺省。
- `ReasoningConfig`：`dialect`（`openai/anthropic-budget/anthropic-adaptive`）、`efforts`（明确允许的档位；不含default）、`budgetTokens`（预算型高档上限，可空）。配置在每个模型保存；未知模型默认null，不因兼容服务返回的模型名字就声明支持。
- `Model/ProbedModel/ModelOption` 提供配置；ModelOption同时提供contextWindow。能力由用户在模型设置中显式声明；未知模型为null，不按任意兼容端点返回的模型名字自动启用。端点协议不匹配的配置在保存时拒绝。
- 设置页可以为选中模型选择无能力、OpenAI effort、Anthropic budget或adaptive，编辑允许档位、预算上限与上下文窗口；沿用整体provider保存和取消草稿，不额外创建写端口。
- `RunRequest.reasoningEffort?` 缺省default。后端独立验证能力与档位；未知/不支持的显式选择返回bad_request，不静默把用户选择吞掉。共享界面切模型后回到default，运行时选择固定，期间禁止修改。
- OpenAI Chat发送`reasoning_effort`，Responses发送`reasoning.effort`；Responses保留`reasoning.encrypted_content`供后续重放。default不发送控制；none仅在能力明确允许时发送none。
- Anthropic预算型发送enabled + budget_tokens；预算须>=1024且小于max_tokens，按档位映射并受模型预算/输出上限约束。adaptive发送thinking.type=adaptive及output_config.effort；none只对声明可关闭的模型发送disabled。
- Anthropic thinking/signature/redacted_thinking、Responses reasoning item、Chat reasoning_content保存到原assistant消息。只在同一端点/模型/协议重放；跨模型不转成普通正文。工具轮中按原顺序保留完整块；取消/失败不把不完整签名块当作完整历史。思考摘要可折叠显示，但不声称供应商公开完整内部推理。

## 3. 用量与上下文合同

- `TokenUsage`：inputTokens、outputTokens、cacheReadTokens、cacheWriteTokens、reasoningTokens，均可null。inputTokens统一为全部输入（含缓存），outputTokens包括reasoning；缓存/思考是明细，不再次加进总数。未知保持null，不填0假装有统计。
- OpenAI prompt/input已包含缓存；Anthropic input_tokens不包含cache read/write，需要加回。多轮逐次累计，单次message_delta为最新快照而非增量相加。
- `ContextUsage`：tokens可null、contextWindow可null、source=`reported/estimated/unknown`、endpointId/modelId。只取最后一次请求的输入+输出，不取多轮累计。
- 无上游输入usage时按实际发送的system/history/input/tools估算，明确显示估算；复用现有字符预算规则，不为此引入tokenizer。`ponytail:`记录该估算天花板。窗口未知不显示百分比；后端32k安全预算不是模型真实窗口。
- 开始新轮、裁剪历史、重新生成和切模型使旧上下文失效；新上下文事件替换而非叠加。失败/取消保留已收到的累计用量但上下文不冒充完整reported。
- 每turn持久化usage、context、实际reasoning选择及端点身份；旧历史迁移保留原input/output，context未知。重新生成清旧结果；会话切换恢复各自统计，不跨实例共享。
- UI占用率0–100钳制仅用于meter；详情保留真实超过窗口的数量。显示当前上下文、输入/输出/缓存/思考、当前会话可统计turn的累计用量；不做无价格依据的金额统计。

### 9.3 差距

1. **线路决定能力。** 我们把“模型族”和“线路协议”绑在一起：Claude 只有走 Messages 线路才识别。Cherry 先按模型 id 定档位，再按线路定写法。这是截图问题的根因。
2. **族表窄。** Cherry 覆盖 gpt-5-pro/codex、Grok、DeepSeek v4、Doubao、GLM、Kimi、Qwen3.8、Gemini 3 等；我们对 `-pro`/`-codex` 直接返回 null。
3. **入口不直达。** 弹层“打开设置”不定位模型；对话框协议名是原始 id。
4. **切模型重置。** 我们切模型回到默认（§2），Cherry 保留并取最近档位。
5. 预算公式、default 不发参数、none 显式关闭、无能力隐藏滑块：两边一致，不改。

### 9.4 设计决策

**移植**

- 族规则与线路写法分离（RT1）：OpenAI Chat/Responses 线路上，凡命中已知推理族的模型 id（去掉 `vendor/` 前缀后匹配），按该族档位生成 `dialect: openai` 配置，请求照现有逻辑写 `reasoning_effort` / `reasoning.effort`。Messages 线路规则不变。default 仍不发参数，所以中转不认该字段时只有用户主动选档才受影响，不会让现有请求变坏。
- 族表按 Cherry 的档位补齐，但只收“写法就是 reasoning_effort 一个字段”的族；Rust `infer.rs` 与 Worker `infer.ts` 同表同测试。
- 设置入口直达（RT2）：弹层“打开设置”带上 endpointId/modelId，设置页打开该线路并弹出该模型的设置对话框；协议下拉显示中文名称；提示文案写明“在模型设置中打开‘推理’能力”。
- 切模型保留并保存档位（RT3，2026-10-22 用户确认）：保存的是“用户选的档位”，不是“当前模型实际用的档位”。发送时按当前模型取实际档位：模型支持就用原档位；不支持就取最近的合法档位，距离相同取较高的一档（Cherry `src/shared/ai/reasoning.ts:34-59` 同规则，避免把“高”降成“关闭”）；模型无能力就是默认、不发参数。切到无能力模型再切回来，原档位仍在。保存位置沿用宿主偏好接口（与 `ai.chat.toolbar` 同一机制），按聊天入口区分，重启后保留；点“恢复默认”才清除。此条取代 §2 的“共享界面切模型后回到 default”。

**暂缓项可行性（2026-10-22 复核）**

先更正上一版：DeepSeek/豆包/GLM/Qwen 的写法不是新协议，它们都走 OpenAI Chat 线路，只是思考字段不同。模型配置里已有 `ReasoningConfig.dialect`（目前 `openai`/`anthropic-budget`/`anthropic-adaptive`），新增写法就是给这个字段加值，再给两端编码器各加一个分支。Cherry 也是同样的做法：写法由线路配置或模型合同决定（`ProviderRegistryService.ts:224-244`），DeepSeek 官方 Chat 线路写 `thinking.type`（`providers/deepseek.ts:26-85`），Qwen 写 `enable_thinking`+`thinking_budget`（`providers/dashscope.ts:92-108`）。

每加一个写法要改的固定位置：Rust `aether-support/src/reasoning.rs`（枚举与校验）、`aether-chat/src/protocol.rs`（编码）、`aether-providers/src/infer.rs`（推断）；Worker `providers.ts`（校验）、`protocol.ts`（编码）、`infer.ts`（推断）；UI `reasoning.ts`、`ModelSettingsDialog.svelte`、i18n。D1/SQLite 存 JSON 文本，不需要迁移。

| 项 | 能否移植 | 做法与代价 | 风险 |
| --- | --- | --- | --- |
| 开关型写法 `thinking.type`（DeepSeek 官方、豆包、GLM、Kimi） | 能，代价小 | 新 dialect `thinking-type`：none→`{"thinking":{"type":"disabled"}}`，其余档位→`enabled`；档位只有关闭/开启 | 中转站可能不认该字段；只在用户选了档位时才发 |
| DeepSeek v4 `thinking.type`+`reasoning_effort` | 能 | 同一 dialect 带一个“也写 reasoning_effort”标志；Cherry 的档位映射 minimal/low→low、medium→high、xhigh→max（`deepseek.ts` `v4EffortMap`） | 映射表要随官方变化维护 |
| Qwen `enable_thinking`+`thinking_budget` | 能 | 新 dialect `qwen-toggle`：none→`enable_thinking:false`；其余→`true`＋预算，预算沿用现有 ratio 计算；Qwen3.8 走普通 `openai` 写法 | Qwen3.8 已转向 `reasoning_effort`，两条规则需按版本区分 |
| 自动识别这些模型 | 能，但需改推断入参 | 豆包/GLM/Qwen 的写法取决于线路域名，不取决于模型 id；现推断只接收 `model_id+protocol`（`probe.rs:221-224`、`store.rs:805-818`），要再传入线路 base_url 的主机名 | 域名表要维护；识别不到时用户仍可在模型设置里手选 |
| `auto` 档 | 能，但只对开关型有独立意义 | 对 `openai` 写法 Cherry 也只是映射成 medium（`reasoningProfiles.ts` `genericEffort`），与现有“中”重复；对开关型/预算型表示“开启、预算由服务商定”。要加枚举值并改三端合同、历史记录可读值 | 合同改动面最大的一项；建议随开关型一起做，不单独做 |
| `ultra` 档 | 能，价值低 | 枚举加值；Cherry 只在 Codex 订阅线路使用（`providers/openai-codex.ts:65-100`），我们没有该线路 | 无法验证真实效果，建议不做 |
| 思考摘要开关 | 能，且修一个现有隐患 | 现在 Responses 线路选档时固定写 `reasoning.summary:"auto"`（`web/src/worker/ai/protocol.ts:322`、`aether-chat/src/protocol.rs:98`）。Cherry 注明第三方 Responses 服务会因此字段返回 400（`reasoningProfiles.ts:148`），只对 OpenAI 官方默认开启。做法：模型配置加 `reasoningSummary: boolean`，默认仅官方域名为真 | 低；属于兼容性修正 |
| serviceTier（服务等级） | 能，但不属于思考强度 | 独立请求字段 `service_tier`（OpenRouter 写请求体、Groq 走 provider option，`providers/openrouter.ts:20-42`、`groq.ts:14-36`），选项按服务商不同，影响计费 | 涉及费用，应单列需求，并在界面标明可能加价 |
| fastMode（快速模式） | 部分能 | Cherry 实现依赖专用通道：Claude Code 订阅、Codex 订阅、豆包 `service_tier:'fast'`（`providers/claude-code.ts:64`、`openai-codex.ts:35`、`doubao.ts:127`）。我们只能做豆包这一种，本质是 serviceTier 的一个取值 | 前两种我们没有对应线路，无法移植 |
| Gemini/Ollama 原生写法 | 不能直接移植 | 我们没有 Gemini 原生线路和 Ollama 线路的出站实现；经 OpenAI 兼容端口接入时按普通 `openai` 写法处理 | 需要先新增线路协议，是另一项工作 |

建议：开关型写法、Qwen 写法、思考摘要开关做成 RT4（`auto` 档随 RT4 一起加），serviceTier/豆包快速模式单列为需求，`ultra` 与 Gemini/Ollama 原生写法不做。

- Cherry 对 claude-sonnet-5.5 的关闭写 `thinking.type:'between_tools'`，与我们写 `disabled` 不同；未见官方文档前不跟改，列入 RT1 核实项。

## 10. 模型资料来源：Modelink 与同类目录（2026-10-22 分析）

### 10.1 Modelink 实际能拿到什么

| --- | --- | --- | --- |
| models.dev `https://models.dev/api.json` | 232 家服务商、9142 条 | 上下文/输出上限、输入输出模态、tool_call、structured_output、`reasoning_options`（如 `{type:"effort",values:[low…max]}`、`{type:"toggle"}`）、官方价格（输入/输出/缓存读写，每百万） | MIT，免鉴权 |
| OpenRouter `https://openrouter.ai/api/v1/models` | 468 条 | 上下文、价格、`supported_parameters`（含 reasoning_effort） | 公开接口 |
| Modelink | 见 10.1 | 见 10.1 | 页面数据无明确许可 |

Cherry 的做法：`packages/provider-registry/scripts/generate-catalog.ts` 在**开发时**从 models.dev 与 OpenRouter 拉取，合并手写规则后生成 `data/models.json` 等文件（1.7 MB）提交进仓库，运行时不联网（`scripts/upstream.ts:79-115` 读取 `reasoning_options`）。

实测：从 models.dev 只取常用十家（anthropic/openai/google/deepseek/alibaba/moonshotai/zhipuai/xai/minimax/mistral）共 253 个模型，精简后 JSON 约 54 KB；Modelink 的 162 个 id 经同一套规范化（去前缀、`.`→`-`、`claude-4-6-opus`→`claude-opus-4-6`）后有 141 个能在 models.dev 命中，未命中的主要是带日期后缀或 `-reasoning/-non-reasoning` 的变体，由族规则兜底。

### 10.3 同步方式比较

| 方式 | 优点 | 问题 |
| --- | --- | --- |
| Worker KV + 定时同步 | Web 端可随时更新 | 桌面端不经过 Worker（未绑定同步时完全离线），两端会读到不同数据；要新增 KV 绑定与定时任务；抓取页面失败时线上数据静默过期；每次部署都依赖第三方可用 |
| 运行时按需查询 | 数据最新 | 每次添加模型都要外网请求；离线不可用；第三方改版直接影响用户 |
| **开发时生成快照、随版本发布**（建议） | 两端同一份数据、离线可用、改动可在 git diff 里审查；与现有共享 fixture `packages/ui/fixtures/model-classify.json` 机制一致；与 Aether docs/21 预设“编译期静态数据、不做运行时远程下载”的决定一致 | 更新需发版；用户可在模型设置里手改覆盖 |

“增量同步”在快照方式下就是：需要时运行一次生成脚本，脚本只写入有变化的模型，提交前看 diff 即是增量。

### 10.4 建议方案

1. 新增 `packages/ui/fixtures/model-catalog.json`（与 model-classify.json 同目录，Rust `include_str!`、Worker 直接 import，同一份数据两端共用）。每条：规范化 id、别名、类型、上下文、最大输出、视觉、工具、思考档位（effort 列表 / 开关 / 预算区间）、官方价格（美元，按百万）。
2. 新增生成脚本 `scripts/sync-model-catalog.mjs`：主源 models.dev（MIT、含思考档位与官方价）；Modelink 公开 `/v1/models` 只用来补 id 别名和上下文，不抓页面数据。只保留常用厂商，输出排序稳定，便于看增量。
3. 读取顺序（探测、读已存模型、运行解析三处共用）：用户在模型设置里保存的值 → 目录命中 → 现有族规则（RT1）→ 未知。目录不覆盖用户已改的值。
4. 价格：目录价写入模型的 `pricing` 默认值，界面标注“官方参考价”；用户线路是中转时可自行改。不做汇率换算（沿用 docs/41 §3.8）。
5. 不做：Worker KV 与定时任务、运行时联网查询、抓取 Modelink 页面数据。

这一步会改变 RT1 的实现：RT1 不再只靠正则族表，而是先查目录、族表兜底。

### 10.5 待确认

1. 是否按 10.4 做（开发时快照、models.dev 为主），还是坚持用 Modelink 页面数据（需接受页面改版失效和条款风险）？
2. 目录默认价格是否写进模型设置（用户可改），还是只在界面显示参考价、不参与费用计算？
